## 2. 我对任务规划的理解

复杂研究不只是“让模型写一篇文章”。它至少包含确定比较维度、收集多方资料、整理证据、对比分析、撰写和核查等环节。只给一个大目标，模型可能跳过搜索、反复查同一内容，或者写到一半忘记尚未完成的工作。

Todo 的作用是把整体工作显式记录下来。它使当前目标、已完成步骤和剩余步骤更容易观察，但不会代替模型执行任务，也不会自动保证报告正确。

本章可以用下面的流程理解：

```text
用户提出研究目标
    ↓
write_todos 建立任务清单
    ↓
搜索资料 → 整理笔记 → 更新完整清单
    ↓
比较分析 → 写入报告 → 读取检查
    ↓
更新清单并输出结果
    ↓
人工核对：清单、工具记录、报告内容是否一致
```

这是一种推荐工作方式，不是框架强制执行的状态机。模型仍可能遗漏步骤，因此必须查看执行证据。

## 3. 研究任务怎样拆解

下面是我为本次实验设计的参考计划，不是一次真实联网运行的逐步日志。

| 步骤 | 具体工作 | 依赖 | 验收条件 |
|---|---|---|---|
| 1 | 明确比较维度：定位、工具、规划、上下文、扩展方式 | 无 | 列出比较口径，不只罗列产品名 |
| 2 | 搜索 Deep Agents 官方资料 | 步骤 1 | 记录来源链接与相关事实 |
| 3 | 搜索 Claude Agent SDK 官方资料 | 步骤 1 | 按相同比较口径整理 |
| 4 | 搜索 Codex SDK 官方资料 | 步骤 1 | 按相同比较口径整理 |
| 5 | 整理共同点、差异和无法确认的信息 | 步骤 2–4 | 形成对照表，不填造无法验证的结论 |
| 6 | 写入 `/notes.md` 和 `/final_report.md` | 步骤 5 | 笔记保留来源，报告有结论和适用范围 |
| 7 | 读回报告并检查遗漏或来源不足 | 步骤 6 | 报告存在且内容符合要求，再更新完成状态 |

拆解时的重点不是任务越多越好，而是每一步都能回答“要做什么、产出什么、怎样判断完成”。例如“研究框架”太笼统；“查阅该框架官方工具调用文档，并把来源及使用方式写入笔记”更容易执行和检查。

如果搜索中发现资料不足，应补充查证任务并保留已完成成果；如果搜索服务报错，应报告阻塞位置，而不是把搜索步骤标为完成。

## 4. TodoListMiddleware 与 write_todos

### 4.1 显式启用

本实验固定的 Deep Agents 0.7.13 需要应用显式加入：

```python
from langchain.agents.middleware import TodoListMiddleware

agent = create_deep_agent(
    model=model,
    tools=[internet_search],
    middleware=[TodoListMiddleware()],
)
```

它提供三个组成部分：`write_todos` 工具、`todos` 状态字段、规划指导提示词。工具可用不代表每个任务都会使用它，具体行为还取决于模型能力和提示词。

### 4.2 状态结构与整体替换

```python
[
    {"content": "收集官方资料", "status": "completed"},
    {"content": "比较差异并写报告", "status": "in_progress"},
    {"content": "读回报告并核验来源", "status": "pending"},
]
```

- `pending`：尚未开始。
- `in_progress`：正在处理。
- `completed`：模型标记已完成，仍需验证。

`write_todos` 更新的是完整清单，不是仅修改某一项。只提交一个新任务时，旧任务不会自动留在清单里；本次离线实验专门验证了这个行为。

三种状态没有自动承诺“依赖已满足”“工具调用成功”或“输出正确”，也没有内置的业务验收器。不要把 UI 上的完成勾选当成研究质量证据。

## 5. 中间件分别负责什么

课程总览图按“能力从哪里配置”分类，不表示运行时的三层先后顺序。

| 配置来源 | 主要模块 | 职责 |
|---|---|---|
| 默认组装 | Filesystem | 文件工具、文件访问相关规则及大结果处理 |
| 默认组装 | Summarization | 达到配置条件后压缩模型输入中的历史 |
| 默认组装 | PatchToolCalls | 补齐历史中缺失的工具响应消息 |
| 专用参数 | SubAgent、Skills、Memory、HITL、AsyncSubAgent | 委派、技能、指导记忆、审批、异步任务 |
| `middleware=[...]` | TodoList、Retry、Fallback、Limits、PII | 规划、重试、备用模型、次数限制、敏感信息处理 |
| 运行时 `checkpointer=` | Checkpointer | 保存与恢复图运行状态；不是中间件列表中的一项 |

缓存等模型相关能力取决于提供方与具体配置，不能只看总览图就认定全部开启。`SubAgent` 默认可能带通用子 Agent，不能理解为“没传 subagents 就一定没有委派工具”。本章示例提示主 Agent 完成研究，未把多 Agent 协作当成作业要求。

同名中间件可以替换默认实例，但这是整个实例的替换，不是把新旧参数逐字段合并。自定义摘要中间件时，必须一起考虑模型、Backend、触发条件和保留策略。

### 5.1 两类 Hook

- Node-style：`before_agent`、`before_model`、`after_model`、`after_agent`，在图中形成节点，适合状态更新、校验等。
- Wrap-style：`wrap_model_call`、`wrap_tool_call`，包裹一次调用，可以通过 `handler` 控制调用或重试。

因此 `agent.get_graph()` 展示的是节点结构，不会自动展开节点内部所有包装逻辑。没有独立摘要节点，不等于没有摘要能力；有节点，也不等于某次执行已经触发摘要。

### 5.2 修补、重试、恢复和验证不是一件事

| 问题 | 处理机制 | 不能据此推断 |
|---|---|---|
| 有工具调用，但缺对应 `ToolMessage` | PatchToolCalls | 工具已经重新执行或外部操作已经撤销 |
| 工具发生可重试异常 | 配置重试策略 | 所有错误都应重试，尤其是无效密钥 |
| 下一次调用要接续状态 | Checkpointer + 相同 `thread_id` | 自动恢复到任意一行 Python 代码 |
| 工具有返回但内容可能错误 | 应用校验、人工审核 | `status=success` 或 `completed` 就代表正确 |

运行取消可能发生在外部服务已处理请求、但结果尚未写回时，因此缺响应不等于没有副作用。对写入、发送等操作，还要考虑重复执行和幂等性。

## 6. 任务规划与上下文管理的配合

长任务会积累搜索结果、工具消息和草稿。文件系统帮助保存较大的内容，摘要机制帮助缩短送给模型的消息，而 Todo 负责单独记录任务进度。

可以把三者理解为：

- `todos` 是进度表：哪些事做了，哪些没做。
- 文件是资料和产物：保存笔记、报告及可回查的历史。
- 摘要是本次模型输入的简化版本：降低长历史占用。

默认对话总结不会删除独立的 `todos` 字段。但“状态中还保存着清单”不等于模型必然正确使用了它，也不等于它每次都以原文自动出现在提示词中。清单过时、更新不完整和模型遗漏仍需要检查。

### 6.1 两种 SummarizationMiddleware

在课程讨论的实现中，LangChain 版本通过 `before_model` 更新消息状态；Deep Agents 版本主要在 `wrap_model_call` 内调整本次模型输入，记录摘要及截断位置，并支持把历史写入 Backend。两者名称相同，但不能把执行位置和保存行为混为一谈。

手工配置时，`trigger` 决定何时尝试总结，`keep` 决定保留多少近期消息。达到触发阈值，但没有可总结的旧消息时，也可能不生成摘要。

本版本比例写法为 `("fraction", 0.85)`，不是旧示例中的 `("ratio", 0.85)`；比例依赖模型窗口信息。窗口未知时，用明确的 tokens 或 messages 阈值更容易实验。手动实例化也不能假定自动继承 `create_deep_agent()` 的默认触发配置。

如果摘要保存历史使用 Backend A，而文件工具读取 Backend B，即使摘要写了路径也不一定能读回。本次摘要测试使用同一个 `StateBackend`，实际检查历史路径可通过 `read_file` 读取。

### 6.2 保存范围

`StateBackend` 是状态中的虚拟文件，不等于本机项目目录中的文件。示例最后显式导出，才会在 `runs/` 下产生本机 Markdown 文件。

同一次运行内可以继续使用状态；多次调用之间自动接续，需要 Checkpointer 和相同 `thread_id`。`InMemorySaver` 只在当前进程内保存，不能用于证明重启后恢复。本次没有测试数据库持久化。

## 9. 问题复盘

### 问题一：PyCharm 提示可能传入 None

`dotenv_values()` 的值可能是字符串，也可能是 `None`。直接把字典项传给要求字符串的模型参数，会触发类型提示。

改进：先把值规范化为字符串，再校验必填项。这样不仅能减少类型警告，也能在发请求前发现缺配置。变量存在不代表密钥有效。

### 问题二：读取 .env 后，os.getenv 仍为空

`dotenv_values()` 返回字典，不会自动写入 `os.environ`。如果读取配置后又用 `os.getenv()` 取值，就混用了两种读取方式。

改进：本实验统一从配置字典取值，不混用，不跨项目找密钥。

### 问题三：导入客户端却执行了另一个脚本

原报错栈显示 `course.py` 导入 `course_example` 中的客户端时，执行了该模块顶层的 `agent.invoke()`。

原因：Python 第一次导入模块会执行模块顶层代码，而不是只提取一个变量。

改进：不要从可直接运行的示例脚本导入客户端；在当前脚本构造客户端。提交版把实际执行放进 `main()`，使用 `if __name__ == "__main__":` 保护。测试导入脚本时不会触发付费调用。

### 问题四：Tavily 密钥被拒绝

模型服务与搜索服务是不同的认证链路。模型能够发出搜索工具调用，并不能证明 Tavily 密钥可用。

排查顺序：确认读取的是当前项目 `.env` → 检查 `TAVILY_API_KEY` 是否填入 → 在 Tavily 账户端确认其有效性 → 再进行最小联网验证。不要在聊天、日志或 GitHub 中公开密钥。

这类鉴权错误不是“缺少工具响应”的同义词；`PatchToolCallsMiddleware` 不能替换或修复 API Key，机械重试通常也无法解决。

### 问题五：消息字段误写为 roles

用户消息应使用 `{"role": "user", "content": "..."}`，不是 `roles`。排查时应沿调用栈确认最早暴露的失败点：先前的导入副作用可能让脚本还没执行到错误字段，就已经在另一个示例中失败。

截至本次整理，学习者当前脚本已去掉误导入，统一从配置字典读取模型参数，并使用 `role`。这些是源码检查结果，不能替代修正后的联网运行证据。

## 10. 学习心得与下一步

我对本章最重要的认识是：规划、执行、保存和验收属于不同职责。Todo 记录“打算做什么、做到哪里”；工具完成具体操作；Backend 保存文件；Checkpointer 负责运行状态接续；报告是否正确仍需要核验。

调试经历也说明，运行失败不一定是任务规划算法的问题。配置读取、模块导入和服务鉴权都可能中断执行。应先看异常最后的具体原因，再结合调用栈定位，不应一看到 LangGraph 或工具节点就判断框架有问题。

下一步需要补齐以下真实结果后，才能把“研究 Agent 实战”标记为完成：

- [ ] 当前项目 `.env` 配置有效，真实模型和搜索请求成功。
- [ ] 实际观察到初始计划和至少一次清单更新，不只看到最终回答。
- [ ] 三种框架均有可核验的官方资料来源。
- [ ] `/notes.md` 与 `/final_report.md` 已生成，报告被读回检查。
- [ ] 人工确认报告没有虚构结论、遗漏对比项或失效引用。
- [ ] 将脱敏后的成功记录和报告补充到作业；不上传完整 `.env` 或未审查日志。

独立练习：把研究主题换成自己熟悉的另一组技术，自己设计拆解和验收条件；再解释为什么 `completed` 不等于正确、为什么换线程后状态不继承。学习者完成后至少隔两天再复述和修改一次，不以本次 AI 整理代替独立考核。
